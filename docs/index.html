V/ENTER WEB 事業部ハンドブック

AI（Claude Code + Codex CLI）でWebサイトを高速・高品質に作るための、実務用一元ドキュメント。

このリポジトリは 「未経験者 + AIエージェント」が見れば即動ける ことを目標に作られています。 迷ったら MAP.md と handbook/ を最初に開いてください。

30秒で分かる V/ENTER WEB

  • 株式会社VAIZO の事業部 の一つ。Webサイト制作を中心事業とする
  • 主軸は AI活用Web制作：Claude Code（司令塔）× Codex CLI（実装ドラフト）の分業
  • 営業手法は カスタマイズデモ + 脆弱性レポート + デザインアイデンティティ の三点セット送付（月次300件規模）
  • ターゲット業態：飲食店・バー・ライブハウス・ホームページ業者制作の店舗サイト
  • 公開実例：retro-backpage.com（仙台レトロバックページ様、2026-04-30公開）

公式サイト vaizo.jp には現時点で Enter Web の記載がないため、対外的な事業概要も社内向けには handbook/00-overview.md で補完しています。

AIエージェント向けの読み方

このリポジトリはAIエージェント（Claude Code、Codex CLI）が読み込んで作業の参照元として使うことを想定しています。

推奨読み込み順（コンテキスト効率重視）:

  1. README.md（このファイル）
  2. MAP.md（全体像）
  3. 当該タスクに関係する handbook/ の該当章
  4. 当該タスクのテンプレ（templates/）
  5. 詰まったら troubleshooting/ と decision-trees/

AIエージェントが守ること:

  • 仕様外の機能を勝手に追加しない
  • TODOで埋めず、その場で完成させる
  • 軍事比喩・否定列挙・採用語・階層用語は使わない（handbook/02-design-policy.md 参照）
  • V/ブランド表記は 半角スラッシュ「/」のみ
  • メールアドレスは info@vaizo.jp を使用（.co.jp は使わない）
  • 飲食/店舗案件は 電話・LINE のCTAを必ず常設
  • 本文 17px / テーブル 15px / 行間 1.9 厳守

1. ミッション

AI（Claude Code + Codex CLI）を実装ドラフト・司令塔として組み合わせ、 飲食・店舗業態を中心に 「速く・安く・上品な」Webサイト を量産する。

「上品な」とは VAIZO Editorial の白黒ミニマルを基調とした審美性であり、テンプレ感を出さないこと。 「速く」とは月次300件規模に耐える生産性であり、人間が手でゼロから書かないこと。

  • 2-2（標準エクスポート）→ コンテンツ部分のみのコピー

4-0. WP最適化版HTMLの作成とデモ確認

【AIにWP最適化を依頼するプロンプト】 → templates/wp-prompts/04-0-optimize.md

最適化要件:

  1. <head>内の meta / link / style を WP テーマと重複しないように整理
  2. <header>/<footer>/<nav> はテーマと統合（削除）
  3. インラインCSSは body スコープ化（body.page-【slug】 .xxx { ... }）
  4. インラインJSはIIFEまたはモジュール化
  5. canonical / og:url / twitter:url / JSON-LD を【公開URL】に書換

  8. GTM / GA タグは既存テーマで設定済みなら削除

  • ブランチ: main
  • パスワード保護する場合は staticrypt 等で

このドキュメントの目的

V/ENTER の営業戦術として、見込み客（飲食店・ライブハウス等）の既存サイトをスキャンし、脆弱性レポートをデザインアイデンティティ・トップページデモとセットで送付する。

この営業手法は、合法かつ誠実に運用すれば成約率を大きく押し上げる強力な手段となる一方、運用を誤ると以下のリスクが発生する：

  • 法的リスク（不正アクセス禁止法違反）
  • 道義的リスク（クライアント側の不快感・SNS炎上・業界での評判低下）
  • 信用リスク（誤検知の指摘で専門性を疑われる）

これらを回避するため、本ドキュメントで定める「2つのライン」を必ず守ること。

ライン1：法的ライン（スキャン手法の制約）

原則

不正アクセス禁止法（日本国法）の対象は「アクセス制御を破る／回避する」行為である。

  • 公開情報を外部から観察する 受動的（パッシブ）スキャン は合法
  • 脆弱性を実際に試す 能動的（アクティブ）スキャン は違法リスクあり

使用OK：パッシブスキャンツール（公開情報の観察）

ツール 用途
securityheaders.com HTTPセキュリティヘッダ評価
Mozilla Observatory 公開情報スコアリング
SSL Labs SSL/TLS設定診断
Lighthouse パフォーマンス／ベストプラクティス／SEO／アクセシビリティ
Wappalyzer / WhatRuns CMS・プラグイン・バージョン検出
sslyze SSL/TLS パッシブモード
WPScan (--no-banner オプション) 公開情報のみ
OWASP ZAP の Passive Scan モード限定 公開情報の観察
ヘッダ取得（curl -I 等の通常HTTPリクエスト） 公開情報

使用NG：アクティブスキャン／攻撃ツール

ツール 理由
sqlmap SQLインジェクション試行
Burp Suite Active Scanner 攻撃ペイロード送信
Nikto Active mode アクティブスキャン
Metasploit エクスプロイト

判断基準（迷ったらこの3問）

  1. このスキャンは外部から見える情報のみを観察しているか？
  2. 攻撃ペイロードを送信していないか？
  3. 認証や制御を突破していないか？

すべて YES なら OK。一つでも NO なら使用しない。

ライン2：道義的ライン（送り方のトーン）

原則

合法であっても、送り方を間違えるとクレーム・炎上の原因となる。

「お役に立てれば」のトーンを守り、押し付け・脅し・直結セールスを避ける。

必須要素：レポートに必ず含めること

  1. 冒頭に「公開情報の範囲で確認しました」と明記する
  2. 「無料の参考資料です」と位置付ける
  3. 「対応は専門業者にご相談ください」と一言入れる（押し売り回避）
  4. 「不要であれば破棄してください」と明記する
  5. パスワード保護をかける（メール本文にパスワードを同送しない／別経路 or 後送）
  6. 非エンジニア向け解消手順書を添付する（橋本CEO設計）

避ける表現

  • 「あなたのサイトは危険です」（恐怖訴求）
  • 「すぐに対応が必要」（煽り）
  • 「うちで全部対応できます」（直結セールス）
  • 「ご返答お願いします」（催促）
  • 専門用語の羅列（手順書で対処）

推奨される表現例

  • 「公開情報の範囲で確認したところ、◯◯の改善余地が見受けられました」
  • 「ご参考までにお送りします。専門業者にご相談される際の材料としてお役立てください」
  • 「ご不要の場合はお手数ですが破棄してください」

送付対象のセーフガード

送付OK

  • 法人の公開コーポレート・店舗サイト（情報を公にしている主体）
  • 飲食・ライブハウス等のV/ENTERターゲット業態（S／A／Bランク）
  • ホームページ業者制作の店舗サイト

慎重対応（送付前に橋本CEO確認）

  • 政府機関・医療機関（公的責任のある機関は別ルール適用）
  • 認証付き会員制サイト（私的領域に該当）
  • 個人ブログ・個人サイト

詳細フロー: decision-trees/vulnerability-target.md

削除依頼SOP

  1. 削除依頼を受けたら、24時間以内に返信
  2. 受信メール・該当データを即削除
  3. ブラックリスト管理シートに登録（OPS_Sheet TASKSタブ「VENTER_BlackList」）
  4. 二度と送付しない（送信リストの除外フラグを永続化）
  5. 削除依頼の文面を記録（後日のクレーム再発時の証跡として保存）

クレーム対応SOP

1次対応：受信から30分以内

  • 小野寺陸斗 or 櫻井みどり が即返信
    • 文面例：「ご連絡ありがとうございます。担当責任者へエスカレーションします」
  • 橋本CEO・櫻井理也CTOへSlack DMで即時通知

2次対応：受信から2時間以内

  • 橋本CEO主導で個別対応
  • 必要に応じて謝罪・削除・関係先への連絡停止
  • 内容によっては顧問弁護士・顧問税理士へ相談

記録

  • クレーム発生案件は OPS_Sheet TASKS に「VENTER_クレーム対応」として記録
  • 月次振り返りで件数・原因を集計、ガイドラインへ反映

再送付ルール

  • 反応がなくても、同一ドメインへの再送付は 3ヶ月以上空ける
  • ブラックリスト登録先は 永久に再送付しない
  • 3ヶ月経過後の再送付は、テンプレを必ず差し替えてから実施する

品質管理（QC）ルール

誤検知の二重チェック

  • 自動スキャン結果は必ず櫻井みどりが目視で確認する
  • 「修正済み」「該当しない」項目はレポートから除外する
  • 1件あたり3〜5分のQC工数を確保する

テンプレ更新

  • スキャンツールの定期メンテナンス（月1回）
  • 業界の脆弱性トレンド反映（CTO 櫻井理也が月次レビュー）
  • ガイドライン違反事例があれば即座にテンプレへ反映

違反した場合の対処

ライン1（法的ライン）違反時

  • 即時に運用停止
  • 該当データを削除
  • 法的リスク評価（顧問弁護士に相談）
  • VAIZO経営陣（橋本CEO・櫻井理也CTO）で対応方針を決定

ライン2（道義的ライン）違反時

  • 該当案件のクレーム対応を最優先
  • 文面・運用ルールを修正
  • 月次振り返りで全社共有

07 — ナレッジ管理・更新運用

本リポジトリを「生きた運用文書」として保つための更新ルール。

1. 基本原則

V/ENTER WEB ハンドブックは 読むためでなく、書き換えるため にある。

  • 案件で詰まった → troubleshooting/ に追記
  • 良いプロンプトを書いた → templates/codex-prompts/ に追加
  • 判断に迷った → decision-trees/ に追加
  • 公開後の学び → runbooks/post-launch-30days.md で振り返り → 各所に反映

「読んだらそのままにしない、必ず1行は変える」 が VAIZER 文化。

2. 更新タイミング

タイミング 更新する場所
案件着手時 runbooks/new-client-kickoff.md のチェックリスト確認、不足項目あれば追記PR
案件中（詰まった時） troubleshooting/ に「何が起きた・どう解決した」を追記
案件公開直後 runbooks/deploy-day.md の改善ポイント、templates/delivery-reports.md で振り返り
公開後30日 runbooks/post-launch-30days.md のフィードバック収集 → 各文書反映
月次 全 VAIZER で15分の振り返りMTG、改善PR を1人1本
四半期 顧問社労士・弁護士・税理士のレビュー反映

3. 更新ワークフロー

軽微な修正（誤字、リンク切れ、追記）

git checkout -b personal/typo-N-handbook-XX
# 編集
git add ...
git commit -m "docs(handbook): 04-wp-publish-guide の typo 修正"
git push -u origin HEAD
gh pr create --fill
gh pr merge --squash --auto  # 自己マージOK

構造変更（新規章追加、章間の関係性変更）

  1. Issue 起票（.github/ISSUE_TEMPLATE/doc-improvement.md）
  2. CTO とSlackで方針確認
  3. ブランチ作成 feature/<issue>-<slug>
  4. 修正 + ローカルビルド確認（npm run build）
  5. PR 作成、CODEOWNERS の自動レビュアーが承認
  6. マージ

新規業態の Codex プロンプト雛形

  1. 1〜2件の実案件で実証（雛形を案件直下で書く）
  2. 案件公開後、雛形を templates/codex-prompts/{業態}.md に汎用化
  3. PR で追加、CTO レビュー
  4. templates/codex-prompts/README.md に業態リスト追加

4. リンク整合性の維持

  • 他ドキュメント参照は相対リンクで書く（書き方は既存ファイルを参照）
  • 絶対URL（https://github.com/...）は外部サービスのみ
  • 月1回 npm run lint:links でリンク切れ検出
  • リンク先のファイル名・パスを変更する場合は、参照側もまとめて修正

5. 公開と機密の境界

詳細は MAP.md §0 鉄則 参照。

GitHub Pages で公開しているため、以下は 絶対に書かない:

  • パスワード・APIキー・OAuth トークン
  • 顧客のメールアドレス（info@example.com 等の汎用は除く）
  • 業務委託パートナーの個人情報（実名以外の連絡先）
  • 案件単価の具体額（範囲表記は可）
  • 競合他社への評価コメント

書いていいもの（公開前提）:

  • 営業手法のフレームワーク
  • AI活用ノウハウ
  • VAIZO Design Policy
  • 公開済みクライアント事例（公開URLが既に出ているもの）

6. 文書のバージョニング

  • ハンドブック全体: CHANGELOG.md に記録
  • 主要文書（02-design-policy.md 等）: 末尾に ## 改訂履歴 セクション
  • セマンティックバージョン: vMAJOR.MINOR.PATCH
    • MAJOR: 構造変更・破壊的変更
    • MINOR: 新規章・機能追加
    • PATCH: 軽微な修正

  • 技術・実装: 櫻井CTO

08 — 経理・請求フロー

09 — クライアントオフボーディング

案件終了・運用契約終了時の標準フロー。属人化を防ぎ、スムーズな引き渡しを実現する。

1. オフボーディングが必要なケース

ケース 主な原因 緊急度
正常終了 制作完了 + 公開後30日のフォロー終了 低
運用契約解約 クライアント側の意思決定 中
トラブル終了 クレーム発展、関係悪化 高
VAIZO 側都合の終了 業務領域外、リソース不足 中
クライアント側の事業終了・倒産 不可抗力 中

2. オフボーディング標準フロー

Day 0: 終了通知

  • クライアント or VAIZO が解約・終了を通知
  • 文書（メール）で記録
  • 案件CTO + 橋本CEO + 経理部に共有

Day 1-3: 引き渡し計画

クライアント側に渡すもの

  • WordPress管理画面ログイン情報（既に渡している場合は再確認）
  • サーバー管理画面ログイン情報
  • ドメイン管理画面の権限移譲（VAIZO が代理取得していた場合）
  • Google Analytics 4 / Search Console / Tag Manager の権限移譲
  • サイトコード一式（GitHub repo の export または ZIP）
  • 画像素材一式（圧縮前の元データ含む）
  • 制作中のドキュメント（議事録 / デザイン提案 / 修正対応表）

VAIZO 側に残すもの・破棄するもの

  • バックアップ .wpress ファイル（30日後に破棄）
  • クライアント情報（個人情報保護法に従い削除 or 匿名化）
  • 1Password Vault Client-{slug} のアクセス権削除（VAIZER 全員）

Day 4-7: 公式引き渡し

  • クライアントとの最終MTG（30分）
  • 引き渡し物リストの確認 → クライアントから「受領確認」のメール
  • 残金請求書発行（handbook/08-finance-billing.md §6）
  • 公開URLの権限移譲確認（DNS / SSL 等）

Day 8-30: アフターケア

  • 軽微な質問対応（無償、契約上の瑕疵担保期間内）
  • 引き渡し後の不具合は追加見積で対応
  • 入金確認

Day 30: 完全クローズ

  • 全データ・権限の VAIZO 側から削除（バックアップ含む）
  • 1Password Vault 完全削除
  • Drive 案件フォルダを「アーカイブ」に移動
  • GitHub Issue を status:closed ラベルでクローズ
  • CHANGELOG / Slack #事業部別_enter-ai で完了報告

3. ケース別の追加対応

A. 正常終了（推奨パス）

  • クライアントから「ありがとう」の温かい引き渡し
  • 月次運用契約への移行を提案（decision-trees/contract-type.md）
  • 公開後3ヶ月・6ヶ月の振り返りMTG提案（次案件・口コミ獲得）

B. 運用契約解約

  • 解約理由をヒアリング（次案件への学び）
  • 「VAIZO サービス改善のため、率直な意見を聞かせてほしい」とアンケート（任意）
  • 解約後の運用引き継ぎ先（次の業者）への協力姿勢

C. トラブル終了（クレーム発展）

詳細は runbooks/incident-response.md を必ず参照。

  • 橋本CEO主導、顧問弁護士相談
  • 文書での記録を徹底
  • 「VAIZO 側の責任」「クライアント側の責任」を明確化
  • 損害賠償・返金の交渉
  • 守秘義務の確認・延長
  • 再連絡禁止リスト追加（handbook/05-vulnerability-scan.md ブラックリスト運用）

D. VAIZO 側都合の終了

  • 30日以上前にクライアントに通知（業界慣習）
  • 後継業者の紹介（VAIZO のアライアンスパートナー）
  • 引き渡し作業を VAIZO 側が責任を持って完了
  • 該当VAIZER のキャリアプランへの影響を内部でケア

E. クライアント側の事業終了・倒産

  • サイト・ドメインの存続意思を確認
  • 売上回収困難なら早期に経理判断（債権放棄 vs 法的回収）
  • 顧問税理士・弁護士相談
  • VAIZO 側のデータ保管期間: 法定 5年または契約に従う

メール雛形

  • アライアンスパートナーとしての継続関係（クライアント側で別案件発生時の優先紹介）

10 — デザインリサーチ：参考と「らしさ」の見つけ方

制作着手前のデザインリサーチで「ゼロから考える」を避ける。VAIZO Editorial を軸にしつつ、業態・店舗の固有性を抽出して提案3案に落とす標準フロー。

1. リサーチの目的

V/ENTER WEB の制作で 「センスで選ぶ」を排除する。3キーワードと3案のテンプレで、誰がやっても同等品質の提案を出せるようにする。

リサーチのアウトプット:

  1. 3キーワード（クライアントの「らしさ」を3語で言語化）
  2. ムードボード（参考画像 6〜12枚）
  3. 提案3案の方向性（例: ELEGANT_WHITE / HERITAGE_DARK / URBAN_MUSIC）
  4. 配色・書体・装飾の決定

所要時間: 1案件あたり 60〜90分（AIを活用すれば 30〜45分）。

判断フロー：「AIに任せる」vs「人間が確認」の境界

handbook/04-wp-publish-guide.md の「迷ったらAI」原則を補足する判断基準。

原則

V/ENTER WEB は 「AIに任せて進める」 が基本姿勢。ただし、人手確認が必須の領域 がある。

カテゴリ別の判断

✅ AIに完全に任せてよい（人手確認不要）

  • HTML / CSS / JS の実装ドラフト生成
  • WP最適化版の作成（4-pre 監査含む）
  • Playwright 全自動テスト（5-AI）
  • 画像のリサイズ・圧縮・WebP変換
  • Lighthouse スコア測定
  • コンソールエラー検出
  • 文章の校正（誤字脱字・口調の統一）
  • 翻訳・要約

⚠️ AIに任せて、人手で必ず最終確認する（QC必須）

  • 脆弱性スキャンレポート: 誤検知の二重チェック（櫻井みどり、3-5分/件）
  • デザインのブランド整合: VAIZO Design Policy 準拠を最終目視
  • コピーライティングの感情・温度: 軍事比喩・否定列挙等の検出
  • クライアント向けメール: 道義的ライン違反の検出（恐怖訴求・煽り等）
  • WP統合方式の選定: AIの推奨を尊重しつつCTOが最終判断
  • 公開前の見た目スクショ: クライアントが認識した最終案と一致するか

❌ AIに任せず、必ず人間が実行・判断する

  • クライアントへの送信 (脆弱性レポート添付メール、提案メール、公開報告)
    • 理由: 道義的判断・関係性・タイミング
  • メール宛先のテスト送信受信確認 (5-メール)
    • 理由: クライアントの実機での受信が最終確認
  • クライアントとの口頭コミュニケーション (会議・電話)
    • 理由: 信頼関係・空気感
  • 法的判断 (削除依頼対応・クレーム対応の最終判断)
    • 理由: 顧問弁護士相談を要する領域
  • 金額・契約条件の最終決定
    • 理由: 経営判断
  • 業務委託契約の指揮命令性に触れる判断
    • 理由: 偽装請負の法的リスク
  • 個人情報の扱い
    • 理由: 個人情報保護法・関係法令

mailto: リグレッション事故の事例と再発防止

仙台レトロバックページ案件（2026-04月、修正ID F-RBP-202605-001/025/026）で発生した実事故の記録。 このページの存在自体が「VAIZO V/ENTER WEB 統合運用フレーム v0.2」の策定動機となった。

事故の概要

何が起きたか

仙台レトロバックページの本番公開後、mailto: リンクから問い合わせメーラーを起動しようとすると 全てのメーラー（Outlook、Gmail、Apple Mail）でメーラーが起動しなくなった。

原因

修正対応 #25 → #26 で、複数宛先の指定方法を以下のように変更した：

<!-- 修正前（動作していた） -->
<a href="mailto:to@example.com,cc1@example.com,cc2@example.com">

<!-- 修正後（動作しない） -->
<a href="mailto:to@example.com?cc=cc1@example.com,cc2@example.com">

カンマ区切りcc → ?cc= 形式 への変更自体は仕様上正しいが、対象環境（Outlook 365 + Apple Mail + Gmail Web）の一部で mailto: URL のエンコードが正しく解釈されない 結果、リンクが無効化された。

影響

  • 公開後 約24時間、お問い合わせフォームが実質機能しないままだった
  • リード喪失の可能性（実害は確認できなかったが、影響度「高」）
  • クライアント・関係者に修正対応で工数発生

なぜ気付くのが遅れたか

  1. 修正対応表（修正ログ）にステータス・優先度・担当・工数の管理がなかった
  2. リグレッションテスト（公開前の mailto: 起動確認）が手順に組み込まれていなかった
  3. Step 5-メール（実機テスト送信）の運用が始まる前の事故だった

教訓

Lesson 1: mailto: の修正は必ず実機で起動確認

  • 修正後、Outlook / Gmail / Apple Mail の少なくとも2環境で起動テスト
  • スマホ実機（iOS Mail、Android Gmail）でも確認

Lesson 2: リグレッションテストを手順に組み込む

handbook/04-wp-publish-guide.md Step 5-メール として正式手順化済み。

Lesson 3: 修正ログの運用標準化

修正ID F-{案件略号}-{YYYYMM}-{連番:03桁} で管理。 ステータス・優先度・担当・工数・スクショを必須項目化。

詳細: メモリ project_vaizo_web_ops.md § C3

Lesson 4: 「公開2週間以内の瑕疵担保」の契約明記

公開後の不具合を「サービス範囲」として無償対応するか、「契約外」として有償対応するかの線引き。 顧問弁護士確認後に契約書に明記。

詳細: メモリ project_vaizo_web_ops.md § W7

WP公開作業のトラブルシューティング

handbook/04-wp-publish-guide.md で詰まったときの対処集。

症状別の対処

1. ログインできない

原因 対処
ID/パスワード間違い 再確認、何度も間違えるとIPロック
IPロック（数回失敗で発動） AIに「Xserver IP ロック解除方法」と聞く、もしくはロック解除依頼をサーバー業者に
ログインURLの変更（セキュリティプラグイン） クライアントに正規URLを再確認

2. 画像のアップロードでエラー

原因 対処
1ファイル容量制限（通常 1GB） サイズダウン、解像度を下げて再試行
サーバー側の容量制限（upload_max_filesize） サーバー業者に相談、もしくは画像を WebP 化
同名ファイル衝突 古いものを先に削除してから再アップ
ネットワーク不安定 10〜15枚ずつ分割して再試行

3. ページが真っ白／500エラー

最優先: 即時復元する。原因調査は後。

Step 1: All-in-One WP Migration の「インポート」を開く
Step 2: ステップ2-1で取得した .wpress ファイルをドラッグ＆ドロップ
Step 3: 復元完了を待つ（数分）
Step 4: 公開URLを別タブで開いて表示確認
Step 5: クライアントに「一時的に乱れたが復旧した」旨を即報告
Step 6: 落ち着いてから原因調査

4. 崩れ・表示異常

症状 第一手
ヘッダー二重表示 統合方式B → 方式Aに切り替え検討 (decision-trees/wp-integration-method.md)
CSS が効かない テーマの優先度に負けている → body.page-{slug} でスコープ化
JS が動かない jQuery 衝突 → IIFE で囲う or テーマ jQuery を回避
画像が出ない パス間違い、ステップ3-1の画像アップロードを再確認
フォントが違う Google Fonts の読み込みがブロックされている可能性、CSP確認

5. プラグイン干渉

プラグイン 干渉ポイント
Yoast SEO meta タグを上書きする → 固定ページ単位で Yoast meta を再設定
Elementor 等 Page Builder ページ全体を Elementor が制御 → カスタムHTMLウィジェットを使うかテンプレート分離
画像最適化系（Smush、EWWW） 画像を勝手に変換 → 個別ファイル除外設定
キャッシュ系（WP Rocket、W3 Total Cache） 古いCSS/JSがキャッシュされる → 該当ページのキャッシュ除外

6. スマホ表示で横スクロール発生

原因 対処
画像・iframe が max-width: 100% 未設定 CSSに img, iframe { max-width: 100%; height: auto; } 追加
テーブルがコンテナ幅を超える overflow-x: auto でラップ
絶対値（px）で固定された要素 レスポンシブ単位（vw、%、clamp()）に置換

7. Lighthouse パフォーマンスが低い

スコア帯 主な原因
50 未満 画像未圧縮、外部スクリプト多数
50-70 LCP 遅延（ファーストビューが重い）
70-90 CLS（レイアウトシフト）、未使用CSS
90+ 維持OK

対処:

  • 画像を WebP 化、loading="lazy"、width/height 明示
  • フォントは font-display: swap、必要最小限のウェイトのみ
  • 不要な外部スクリプト削除（GTM、ヒートマップ等を最低限に）
  • Critical CSS をインライン化、それ以外は遅延読み込み

復元手順（バックアップから戻す）

A. 完全復元（致命的不具合）

1. WP管理画面の「All-in-One WP Migration」→「インポート」
2. ステップ2-1で保存した .wpress ファイルをドラッグ＆ドロップ
3. 復元完了まで待つ（数分〜数十分）

Codex CLI トラブルシューティング

handbook/03-codex-claude-workflow.md の補足。

1. 無音失敗（最も多い）

症状

codex exec を実行しても、出力ファイル（codex_out.md）が空・もしくは作られない。エラーメッセージも出ない。

原因

ChatGPT セッションが切れている。

対処

# 1. バージョン確認（疎通確認）
codex --version

# 2. 再ログイン
codex login
# → ブラウザが開く → ChatGPT アカウントでログイン

# 3. もう一度 exec
codex exec --skip-git-repo-check --cd "$PWD" --output-last-message "./codex_out.md" "$(cat ./codex_prompt.md)"

予防策

各案件の起動前に毎回 codex --version を打つ。

2. --cd 未指定で意図しないディレクトリが編集される

症状

Codex が案件と無関係の場所（ホームディレクトリ等）にファイルを作成する。

原因

--cd オプションを付け忘れ、Codex の現在ディレクトリが意図しない場所だった。

対処

# 必ず --cd "$PWD" を付ける
codex exec --skip-git-repo-check --cd "$PWD" --output-last-message "./codex_out.md" "$(cat ./codex_prompt.md)"

PowerShell の場合:

codex exec `
  --skip-git-repo-check `
  --cd "$PWD" `
  --output-last-message ".\codex_out.md" `
  (Get-Content .\codex_prompt.md -Raw)

3. 対話モードに入って制御不能

症状

codex を引数なしで起動するとREPL（対話モード）に入り、Claude Code から制御できない。

対処

必ず codex exec（非対話モード）を使う。exec を忘れない。

# NG: 対話モードに入る
codex "..."

# OK: 非対話モード
codex exec --skip-git-repo-check --cd "$PWD" --output-last-message "./codex_out.md" "..."

4. Playwright モジュールが読み込めない

症状

Codex が出力したコード末尾に「Playwright確認は環境で playwright モジュールを読み込めず未実施です」と書かれる。

原因

Codex CLI のサンドボックス環境内に Playwright がインストールされていない。

対処

Playwright によるブラウザ確認は Claude Code 側 + Playwright MCP で実行する。Codex 側ではドラフト生成のみに留める。

1. Codex は HTML/CSS/JS を生成するのみ
2. Claude Code が Playwright MCP を使ってブラウザで確認
3. スクショ・コンソールエラー検出は Claude 側で

詳細: troubleshooting/playwright-failures.md

5. ChatGPT Plus 容量枯渇

症状

codex exec を打つと「Rate limit exceeded」「Quota exceeded」のようなエラー。

対処

handbook/03-codex-claude-workflow.md §9 のフォールバック順:

  1. Claude Opus 4.7 で直接実装（VAIZER 1名 月 $20 で利用可能）
  2. それも不可なら Gemini 3.1 Pro Preview をフォールバック

容量回復は通常 24時間後。緊急ならClaude/Geminiに切替。

Playwright 関連のトラブルシューティング

templates/wp-prompts/05-ai-test.md や handbook/03-codex-claude-workflow.md で Playwright が使えない場合の対処。

1. Codex 環境で Playwright モジュールが読み込めない

症状

Codex が「playwright モジュールを読み込めず未実施」と出力。

原因

Codex CLI のサンドボックス環境に Playwright がインストールされていない。

対処

Claude Code + Playwright MCP で代替する：

  1. Claude Code 側に Playwright MCP を有効化
  2. templates/wp-prompts/05-ai-test.md のプロンプトを Claude Code に直接投げる
  3. Claude が Playwright MCP 経由でブラウザ起動・テスト・スクショ取得

代替手段（ローカル Playwright）：

npm init -y
npm install -D playwright
npx playwright install chromium

# テストスクリプトを書いて実行
node test-script.mjs

2. ローカルで Playwright がブラウザを起動しない

症状

playwright install 済みなのに browser.launch() が失敗する。

原因 / 対処

原因 対処
Chromium がインストールされていない npx playwright install chromium
ヘッドレスモードで動かない（Linux） xvfb-run で実行、または headless: true
Windows でパス問題 playwright install を管理者権限で再実行

3. Lighthouse スコアが取得できない

症状

Playwright Lighthouse プラグインが動かない。

対処

代替: PageSpeed Insights API を使う

curl "https://www.googleapis.com/pagespeedonline/v5/runPagespeed?url={{公開URL}}&strategy=mobile"

または PageSpeed Insights の Web UI:

  • https://pagespeed.web.dev/

4. ヘッドレスでスクショが乱れる

症状

page.screenshot() がデバイスピクセル比やフォントレンダリングで実機と異なる。

対処

const browser = await chromium.launch({ headless: true });
const context = await browser.newContext({
  viewport: { width: 375, height: 812 },
  deviceScaleFactor: 2,         // Retina 相当
  isMobile: true,
  hasTouch: true,
  userAgent: 'Mozilla/5.0 (iPhone; CPU iPhone OS 16_0 like Mac OS X) ...',
});

特定の幅でテストする場合:

const widths = [320, 375, 414, 768, 1024, 1280, 1920];
for (const width of widths) {
  const context = await browser.newContext({ viewport: { width, height: 800 } });
  const page = await context.newPage();
  await page.goto('{{公開URL}}');
  await page.screenshot({ path: `screenshot-${width}.png`, fullPage: true });
}

5. CORS / mixed content エラー

症状

Playwright で外部リソース（Google Fonts、CDN画像）が読み込まれない。

対処

  • --ignore-certificate-errors を Chromium 起動オプションに追加
  • もしくはローカルプロキシ経由でリソースを配信

6. Playwright が遅い・タイムアウト

対処

// タイムアウトを延長
page.setDefaultTimeout(60000);  // 60秒

// 不要なリソースをブロック
await page.route('**/*.{png,jpg,jpeg,gif,webp}', route => route.abort());

LCPが遅い原因が画像なら、それ自体が課題なので画像最適化を先に。

Runbook：1Password Teams 契約・セットアップ手順書

Phase 1 で実行する。櫻井CTOが主導、橋本CEOが予算承認。

なぜ 1Password Teams か

現状、WP管理画面ログイン情報・サーバー認証情報・SaaSログインが各個人PCのローカル（C:\Users\hashi\.vaizo\secrets\等）に分散して保管されている。

これは以下のリスクをはらむ：

  1. アクセス不能リスク: 担当者の個人PCに障害が起きたら他のメンバーが対応できない
  2. 二重管理リスク: 複数人で同じ案件を扱う際、最新パスワードがどこにあるか分からない
  3. 退職時リスク: メンバーが退職した際、当人が握っていた認証情報の引継ぎが煩雑
  4. 監査ログ不在: 誰がいつどのパスワードを参照したかの記録がない

1Password Teams を導入することで上記すべてに対応できる。

コスト試算

  • プラン: 1Password Teams Business
  • 料金: 月額 $7.99/ユーザー（年契約）または $9.99/ユーザー（月契約）
  • VAIZER 5名: 月額 $40 〜 $50（年間 $480 〜 $600）

橋本CEO予算承認後に契約。

セットアップ手順

Step 1: トライアル契約（櫻井CTO）

  1. https://1password.com/teams/ にアクセス
  2. 「Try free for 14 days」をクリック
  3. 必要情報を入力:
    • チーム名: VAIZO
    • 管理者メール: info@vaizo.jp 配下の管理者専用アドレス（例: admin@vaizo.jp）
    • 言語: 日本語
  4. クレジットカード登録（トライアル中は課金されない）
  5. 「Secret Key」を安全な場所に保管（重要）

Step 2: Vault 設計（櫻井CTO）

トライアル開始後、Vault 構造を以下のように作成：

Vault名 内容 アクセス権
Personal 個人用（既定） 各個人
Shared 全員アクセス可（既定） 全VAIZER
VAIZO-Internal 社内ツール管理者権限（GitHub・Slack・Drive 等） 経営陣（橋本CEO・櫻井CTO）
Enter-Web-Operations 共通の運用認証（VAIZO自体のサーバー・ドメイン） VAIZER 5名
Client-{slug} 案件ごとの認証情報 案件アサイン者のみ（必要時招待）

Step 3: VAIZER 招待（櫻井CTO）

  1. 1Password Web画面 → 「Admin Console」→「People」→「Invite Member」
  2. 各VAIZER のメールアドレスを入力
  3. デフォルト Vault は Personal + Shared
  4. 個別案件の Vault は案件アサイン時に追加

VAIZER 招待リスト（Phase 1 時点）:

  • 橋本友太郎（CEO）
  • 櫻井理也（CTO）
  • 櫻井みどり（制作）
  • 小野寺陸斗（制作）
  • OneBe代表（必要時のみ案件単位で）

Step 4: 既存 secrets の移管（櫻井CTO + 橋本CEO）

  1. C:\Users\hashi\.vaizo\secrets\ にある全認証情報をリストアップ
  2. 各ファイルを 1Password の対応 Vault に新規アイテムとして登録
  3. アイテム種別:
    • WP管理画面: Login カテゴリ（URL + ユーザー名 + パスワード）
    • サーバー: Server カテゴリ
    • APIキー: API Credential カテゴリ
  4. 移管確認後、ローカルファイルは 暗号化バックアップ → 削除
    • ローカルバックアップ先: C:\Users\hashi\.vaizo\secrets-archived\encrypted.zip（パスフレーズ保護）
    • その後、secrets\ フォルダの中身を削除（フォルダは残す）

Step 5: 1Password CLI 導入（任意・実装担当者）

スクリプトから認証情報を呼び出せるようにする：

# Windows (winget)
winget install AgileBits.1Password.CLI

# 動作確認
op --version

# サインイン
op signin

スクリプトでの使用例:

# WP管理画面パスワードを環境変数にセット
export WP_PASSWORD=$(op read "op://Client-RBP/wp-admin/password")

# Codex CLI で参照
codex exec ... --env "WP_PASSWORD=$WP_PASSWORD" ...

Step 6: 運用ルール周知（櫻井CTO）

鉄則

  1. 本番認証情報は Slack/メール/Drive/GitHub に直接貼らない
  2. 認証情報を渡したい時は 1Password の「Share」機能で時限式リンクを生成
  3. 退職・契約終了時は該当 Vault からの権限削除を即実行
  4. 2要素認証（2FA）必須: 全ユーザーに対して強制設定
  5. Master Password は Slack/メール/Drive に書かない

教育

  • 全VAIZER に handbook/06-onboarding.md の更新版を周知
  • 30分の Zoom セッションで全員の初期セットアップを支援

Step 7: 14日トライアル後の本契約判断（橋本CEO）

トライアル14日後に：

  • 利用率（誰が何を保管したか）を確認
  • コスト・運用負荷とリスク低減のバランスを評価
  • 本契約 or 別ソリューション（Bitwarden Teams、社内自前 等）を判断

本契約推奨: 月額 $40-50 で得られるリスク低減は十分に見合う。

Runbook：クレーム・障害発生時の対応

営業送付・案件中・公開後で発生したクレーム・障害への対応標準フロー。 「沈黙が一番のリスク」が原則。素早い1次返信を最優先。

1. インシデント分類

種類 優先度 主担当 エスカレーション
削除依頼（脆弱性レポート受領者） 中 小野寺・櫻井みどり 24時間以内に対応、ブラックリスト永久登録
クライアントクレーム（軽度） 中 案件CTO 30分以内に1次返信 → 2時間以内に方針返答
クライアントクレーム（重度） 高 橋本CEO主導 30分以内に1次返信 → 2時間以内に橋本CEOから直接対応
公開サイト障害（500エラー等） 最高 案件CTO バックアップから即復元 → 5分以内にクライアント連絡
法的トラブル（損害賠償等） 最高 橋本CEO 顧問弁護士に即相談
第三者からの権利侵害告知 高 橋本CEO 24時間以内に内部調査 → 顧問弁護士相談
SNS炎上・ネガティブ拡散 高 橋本CEO 沈黙せず、状況を確認したうえで誠実な対応

2. 一般原則

2.1 沈黙しない

  • 1次返信は「内容ある返答」でなくてよい
  • 「ご連絡ありがとうございます。担当責任者へ即エスカレーションします。本日中に方針をご返答いたします」で十分
  • 沈黙は責任放棄に見える → 関係を破綻させる

2.2 嘘をつかない

  • 「すぐ直します」と言って直せないと信頼ゼロ
  • 「現在調査中です。○時までに状況をご報告します」と時刻を切る
  • 状況不明なら「不明である」と正直に伝える

2.3 文書で記録する

  • すべてのやり取りはメール or Slack で文書化
  • 電話・対面の場合は終了直後に「本日のお電話の内容を整理させていただきます」とメール送付
  • 法的トラブルの可能性があればDriveに証跡保存

2.4 個人で抱え込まない

  • 担当者が一人で対応しない（バーンアウト・判断ミスの原因）
  • すぐに案件CTO・橋本CEOに共有
  • 共有=責任分散ではない、判断の質を上げる

3. 削除依頼（脆弱性レポート受領者）

3.1 受領メール例

「貴社からのメールは不要です。今後一切送らないでください。」

3.2 対応手順（24時間以内）

1. 即返信（30分以内）
   雛形: 「ご連絡ありがとうございます。直ちに送付リストから除外し、頂いたメール・データはすべて削除いたします。
          ご不快な思いをさせてしまい、誠に申し訳ございません。」

2. ブラックリスト登録（OPS_Sheet TASKS タブ「VENTER_BlackList」）
   - ドメイン
   - 受領日
   - 削除理由（簡潔に）

3. 受領メール・添付データ・関連スクショを削除

4. 案件CTO に Slack DM で報告

5. 月次振り返りで件数集計・傾向分析

3.3 二度と送付しない

  • ブラックリスト登録先は 永久に再送付しない
  • 別担当者が知らずに送付しないよう、ターゲットリスト作成時に必ず照合

3.4 詳細

handbook/05-vulnerability-scan.md §削除依頼SOP

4. クライアントクレーム（軽度）

4.1 例

  • 「この修正、思っていたものと違います」
  • 「お問い合わせフォームから来たメールが届かないようです」
  • 「Lighthouse のスコアが思ったより低いですが」

4.2 対応手順

1. 30分以内に1次返信
   雛形: 「ご連絡ありがとうございます。直ちに状況を確認し、本日中に方針をご返答いたします。
          ご不便をおかけし、申し訳ございません。」

2. 案件CTO + 橋本CEO に Slack DM で共有

3. 状況調査（〜2時間）
   - 該当箇所のコード確認
   - 公開URLでの再現確認
   - AIテストレポート再走（templates/wp-prompts/05-ai-test.md）

4. 2時間以内に方針返答
   - 原因（VAIZO側 / クライアント側 / 第三者起因）
   - 対応方針（即修正 / 翌営業日対応 / 追加見積）
   - スケジュール（〇月〇日までに対応完了）

5. 修正実施 → 完了報告

6. 修正対応表（修正ID `F-{案件略号}-{YYYYMM}-{連番:03桁}`）に記録

5. クライアントクレーム（重度）

5.1 例

  • 「サイトに掲載された内容で営業損失が出た」
  • 「契約書と異なる成果物だ。返金してほしい」
  • 「弁護士に相談している」

5.2 対応手順

1. 30分以内に1次返信（小野寺・櫻井みどりが）
   雛形: 「ご連絡ありがとうございます。担当責任者の橋本へ即エスカレーションいたしました。
          本日中に直接ご連絡を差し上げます。」

2. 橋本CEO に電話連絡（即時）

3. 2時間以内に橋本CEOから直接対応
   - 電話 or 対面でヒアリング
   - 文書でやり取り内容を記録
   - 顧問弁護士への事前相談（「念のため」レベルでよい）

4. 状況評価
   - VAIZO側の責任 → 謝罪 + 修正 + 必要なら返金・損害賠償
   - クライアント側の認識違い → 契約書・議事録で事実確認 + 丁寧な説明
   - グレーゾーン → 弁護士相談 + 妥協点の協議

5. 文書で合意形成
   - 解決方法を文書化（メール・覚書）
   - 双方の合意を記録

6. 振り返りで再発防止策を立案
   - troubleshooting/ に追加
   - 契約書・運用フローの改善

5.3 やってはいけないこと

  • ❌ 一人で抱え込む（必ず橋本CEOに即報告）
  • ❌ 感情的な返信（24時間ルール: 強い感情があれば1日寝かせる）
  • ❌ 法的判断を素人で行う（顧問弁護士相談が安い投資）
  • ❌ SNS で言い訳・反論（炎上拡大）

6. 公開サイト障害（500エラー・真っ白等）

6.1 検知タイミング

  • クライアントからの通報
  • VAIZO側の監視（Phase 3 で導入予定）
  • 自動テスト（GitHub Actions、Phase 3 予定）

6.2 対応手順（最優先）

1. 復元（5分以内）
   - All-in-One WP Migration の「インポート」を開く
   - 公開当日に取得した .wpress バックアップから復元
   - 復元後、公開URL で表示確認
   詳細: troubleshooting/wp-publish-issues.md

2. クライアント連絡（10分以内）
   雛形: 「公開サイトに一時的に表示の乱れが発生しましたが、復旧いたしました。
          原因を調査の上、本日中に詳細をご報告いたします。
          ご心配をおかけして申し訳ございません。」

3. 案件CTO + 橋本CEO に Slack DM 並行報告

4. 原因調査（落ち着いてから）
   - WP更新による互換性破壊
   - プラグイン更新の干渉
   - サーバー障害
   - ハッキング（その場合はサーバー業者連絡）

5. 復旧策・再発防止策を立案
   - troubleshooting/wp-publish-issues.md に追加
   - 該当案件の修正対応表に記録

6.3 ハッキングが疑われる場合

  • 即サーバー業者に連絡（SSH切断・ログ取得）
  • 顧問弁護士相談
  • 警察相談（被害届の検討）
  • クライアントにも直接報告
  • パスワードを全更新

7. 法的トラブル（損害賠償・訴訟等）

7.1 受領内容例

  • 内容証明郵便
  • 弁護士からのメール
  • 訴訟通知

7.2 対応手順

1. 受領後、即橋本CEOへ
   - 自分で返信せず、橋本CEOの判断を待つ
   - 受領した文書を Drive 案件フォルダ「法的対応」に保管

2. 顧問弁護士に即相談
   - 24時間以内に1回目の相談MTG
   - 内容と影響評価
   - 対応方針の決定

3. 文書での回答
   - 顧問弁護士監修の上で回答
   - 期限内（通常2週間）に返答

4. VAIZER 全員に共有
   - Slack #all-株式会社vaizo で簡潔に状況共有
   - 全員が「黙る」協力体制（外部に話さない）

5. 解決後の振り返り
   - 契約書・運用フローの改善
   - 経営判断としての教訓

8. 第三者からの権利侵害告知

8.1 例

  • 「公開しているサイトの画像に、当方の著作物が無断使用されている」
  • 「文章が剽窃されている」
  • 「商標権を侵害している」

8.2 対応手順

1. 24時間以内に1次返信（橋本CEO主導）
   雛形: 「ご連絡ありがとうございます。直ちに内部調査を行い、
          〇〇月〇〇日までに方針をご返答いたします。」

2. 内部調査（48時間以内）
   - 該当画像・文章のソース確認
   - 提供先（クライアント側 / フォトストック / VAIZO側生成）の追跡
   - 著作権・商標権の所在確認

3. 顧問弁護士相談

4. 結論
   - 事実関係に誤り（VAIZOに非なし）→ 丁寧な説明 + 証拠提示
   - 一部に問題あり → 該当箇所削除 + 謝罪 + 再発防止
   - 全面的に問題あり → 削除 + 謝罪 + 必要なら賠償

5. クライアントへの報告
   - 該当箇所がクライアント素材由来の場合、原因を共有

9. SNS炎上・ネガティブ拡散

9.1 検知

  • VAIZER 自身の発見
  • クライアントからの通報
  • Google アラート（vaizo / V/ENTER で設定推奨）

9.2 対応手順

1. 状況確認（拡散規模・内容の正否）
   - スクショ取得（証跡保存）
   - 発言者の意図・背景を確認

2. 沈黙ではなく、誠実な対応
   - 状況に応じた返答（謝罪 / 説明 / 訂正依頼）
   - 第三者を巻き込まない

3. 橋本CEO + 顧問弁護士相談
   - 反論すべきか / 沈静化を待つか / 法的対応か

4. 全VAIZER で連携
   - Slack #all-株式会社vaizo で状況共有
   - 個人SNSでの反論禁止（炎上拡大）

5. 解決後の振り返り
   - 文体・運用ルールの改善
   - 再発防止
